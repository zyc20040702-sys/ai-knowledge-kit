# 固定规则（可复用）

> 只写已经验证过、可重复执行的「遇到 X 就做 Y」。
> 任何 AI 在担任**知识库维护人**时，均可按本文件执行。
> 具名 bot 对照表、群聊口令、私有仓硬规则请放在你的**私有知识库**，本文件不收录。

## 知识库操作

1. 遇到「从零搭库 / 把文件夹变知识库」→ 按 `skills/shengjiang-knowledge/SKILL.md`：先定根目录 → 只读审计 → 预览 → 再写入。
2. 遇到「接一批资料」→ 先 `scan_materials.py` 建清单，再给接入预览，确认后索引；原件默认不搬家。
3. 遇到「库还能不能用」→ 跑 `audit_knowledge_base.py`；超过 7 天未检查时提醒一次。
4. 用户纠正 AI → 立刻记入私有库的 `system/MEMORY_LOG.md`；同类达 3 次提议升为固定规则。

## Skill 分岗原则

原则：**每个角色只跑自己岗位需要的用户工作流 Skill**；需要别人岗位能力时交接或请用户点名，不跨岗并行开跑。

建议在私有库维护一张「Skill → 默认主责岗位」对照表。下表仅为**岗位类型示意**（请换成你自己的角色名）：

| Skill / 能力族 | 默认主责岗位（示例） | 可协作 / 只读 | 不要主动跑 |
| --- | --- | --- | --- |
| `shengjiang-knowledge` | 知识库维护人；个人资料岗 | 全员可读库 | 非维护人勿改入口/结构/巡检状态 |
| `shengjiang-research` | 视频文案岗；产品经理岗（对标时） | 内容岗读产物 | 非主责勿发起付费采集 |
| `shengjiang-viral-breakdown` | 视频文案岗；编剧岗；视频剪辑岗 | 产物可入库 | 非内容角色勿主动拆片 |
| 学术成稿族 | 主管岗 / 写作岗 | 知识库维护人管结构 | — |
| 小程序开发 / 虚拟支付 | 软件开发岗 | — | 非开发勿擅自改工程 |
| Impeccable / Taste | 前端设计岗 / 视觉设计岗 | 互相交接 | — |
| product-market-ops | 产品经理岗 | 设计/工程消费交接件 | — |
| MoneyPrinterTurbo 短视频 | 视频制片岗（一条龙入口）；视频剪辑岗（并列可跑成片）；视频文案岗（脚本侧） | 素材归档可协同知识库维护人 | 非内容角色勿擅自批量渲片 |
| find-skills | 待确认 | — | 未确认主责前不广播开跑 |

交接约定：

5. 调研产物、拆解稿要长期留用 → 交知识库维护人索引进 `01.资料库` 或 `03.项目档案`。
6. 用户点名「某某岗位做某事」→ 以点名为准，覆盖默认主责。
7. 同一任务两人都能做 → 先看点名；未点名按主责，另一人只供材料。

## 知识库维护人常驻职责

8. 发现 Skill 新增 / 改名 / 删除 → 当日更新私有库对照表与清单，并记变更日志。
9. 新 Skill 归属不明 → 先标「待确认主责」，问用户后补全。
10. 对照表有实质变更 → 简短 FYI **受影响主责岗位**（不必全员群发）。
11. 每周例行对照 Skill 目录与清单；无变化可安静。
12. **每周例行整理**：断链、Skill 对照、项目是否缺源码包、入口一致性；定点检查，不是全库内容审查。

## 项目源码包留档

13. 项目有实质代码变更或用户要求留档 → 确认 `03.项目档案/<项目>/` 内有最新**无密钥**可复原源码包。详见 `03.项目档案/README.md`。

## 检索优先与分层归档

### 四级分层

1. **入口层**（极薄）：`AGENT.md` / `INDEX.md` / `system/PROCEDURES.md` /（私有）周重点与同步约定
2. **索引层**：主题索引、Skill 清单 / 分岗对照、项目档案 README —— 回答「去哪找」
3. **结论层**：决策摘要、交档状态、版本号、踩坑结论 —— 短句、可引用、带出处路径
4. **原件层**：源码包、长文、截图、导出物 —— 只存库内文件；默认不进记忆 / 对话正文

### 检索优先工作流

14. 接到知识任务 → **先**读入口薄文件 → **再**查索引 → **再**打开命中路径的原件 → 必要时才跑**定向**巡检。
15. **禁止**无明确任务目标时对全库做 `find` / `rg` / 递归浏览；**禁止**把大 zip / 长文塞进记忆或对话正文。

### 记忆写入白名单

16. **可写**：根路径、私有真相源约定、进行中项目名 + 档案路径、Skill 主责结论、最近健康结论（带日期）。
17. **不可写**：源码内容、整篇文档、密钥、可从 INDEX 推导的整棵目录树。

### 归档与体积

18. **进行中项目**：决策与轻量灾备 zip 放 `03.项目档案/<项目>/`。
19. **已结项**：结论进索引层；大包可迁外部存储并在档案留链接。
20. **收件箱**：未归属材料应催归档，避免变成第二全库。

### 巡检边界

21. 周例行是定点检查：断链、Skill 对照、缺源码包、入口一致性 —— **不是**全库内容审查。
22. 健康结果写入私有库 `system/state/`；对外只报 P0 / P1 摘要。

## 协作边界

23. 对外发消息、破坏性覆盖、移动原件 → 必须有用户明确授权。
24. `shengjiang-research` 任何可能扣费的批量请求前 → 先给请求数与费用预览；仅主责在用户确认后执行。

## 不熟悉功能：先检索再实现

> 适用于**开发 / 工程实现**角色。纯知识库维护、文案、设计不适用「从零实现功能」场景。

25. 遇到**不熟悉**的功能、协议、SDK、支付、媒体处理等 → **禁止**立刻从零手写完整实现。先检索**维护活跃、许可证明确**的同类开源项目，至少比较：实现思路、依赖与技术栈、已知问题、弃用与兼容风险。
26. **优先借鉴**经过验证的设计与架构取舍；可引用、适配**许可证兼容**的接口形状与模块划分。
27. **禁止**直接复制：许可证不明或不兼容、来路不明、长期停更且无替代说明、或与当前技术栈明显不兼容的代码。借鉴须注明来源仓库与许可证。
28. 检索结论写入项目档案或任务答复；确实无合适候选时再说明为何从零，并列出主要风险后再动手。
